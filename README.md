# local-llm-actuary

A practitioner's companion for running, using, and fine-tuning local large language models for actuarial work. Everything here runs on your own hardware; nothing you type, paste, or train on leaves your machine.

Companion repository to *The Actuary's Local LLM*, published in two parts. [Part 1: Confidential AI on Hardware You Control](https://globebyte.com/insights/the-actuarys-local-llm-part-1-confidential-ai-on-hardware-you-control) makes the case for keeping confidential work on hardware you own, and covers the four layers of a local setup, the hardware that actually matters, and the thirty-minute install. [Part 2: Fine-Tuning When Prompting Is Not Enough](https://globebyte.com/insights/the-actuarys-local-llm-part-2-fine-tuning-when-prompting-is-not-enough) picks up where prompting runs out, with a measured case study: a fine-tuned 4B model matching a prompted 8B baseline at 95 per cent accuracy after 99 seconds of training, and the auditability you trade away when the rules move from a prompt into the weights.

## Why local

Some actuarial work should not leave organisational control regardless of any vendor's assurances: claim narratives containing personal information, experience-study commentary, draft reserving methodology, anything commercially sensitive or subject to data-residency obligations. A local model changes the shape of the question. The weights run on your machine, the prompt never crosses the network, and the trust boundary you have to defend is the one you already defend for every other confidential system. You also get cost predictability, offline access, and the learning value of seeing how these systems actually behave.

A local 8B-class model is not a frontier model and will not match one on open-ended reasoning. For narrow, well-specified tasks, which are precisely the tasks worth automating, the gap closes sharply, and this repository is built around such tasks.

## Quickstart

Full instructions, hardware tiers, and troubleshooting in [00_install.md](00_install.md).

```bash
ollama pull qwen3:8b
ollama pull nomic-embed-text
git clone https://github.com/globebyte/local-llm-actuary.git
cd local-llm-actuary
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python examples/01_first_query.py
```

## The examples

| # | Script | Practice area | What it demonstrates |
|---|---|---|---|
| 01 | [`examples/01_first_query.py`](examples/01_first_query.py) | Any | The OpenAI-compatible bridge: cloud code runs unchanged against localhost |
| 02 | [`examples/02_claim_classification.py`](examples/02_claim_classification.py) | GI / P&C | Classifying free-text claim notes into reserving categories with a strict output contract, validation in code, and measured accuracy |
| 03 | [`examples/03_methodology_qa.py`](examples/03_methodology_qa.py) | Life / health | Question answering over a confidential methodology document: local retrieval, mandatory citations, and an explicit "not covered" exit |
| 04 | [`examples/04_governance_wrapper.py`](examples/04_governance_wrapper.py) | Any | A call that can be refused, not merely logged: the model digest pinned to an approved build, output required as structured JSON with citations resolved in code, a hash-chained audit log, and nothing usable until a named reviewer signs off |

Each example has a companion explainer that walks through what it does, why each design choice was made, how to read the output, and where it falls short: [01](examples/01_first_query.md), [02](examples/02_claim_classification.md), [03](examples/03_methodology_qa.md), [04](examples/04_governance_wrapper.md). Read alongside the script; they are written for actuaries rather than for developers.

All examples default to `qwen3:8b` and read `LLM_BASE_URL` / `LLM_MODEL` from the environment, so they work with Ollama, LM Studio's server, or any OpenAI-compatible endpoint. Examples 02 and 03 have `--dry-run` modes that show their prompts and chunking without a model call.

## Fine-tuning

When prompting is not enough (format discipline, domain vocabulary, small-model economics), [`finetune/`](finetune/README.md) contains the full QLoRA recipe: dataset preparation, training Qwen3-4B on the synthetic claims, GGUF export back into Ollama, and a side-by-side evaluation of the fine-tuned 4B against the prompted 8B on a held-out test set. Paths for local NVIDIA GPUs, free Colab (synthetic data only, and the README explains why that caveat is the whole point), and Apple Silicon via MLX. Its companion explainer, [`fine_tuning_explained.md`](finetune/fine_tuning_explained.md), covers the hyperparameters, the measured results, and the failure modes in the same detail as the example write-ups.

## Data

Everything in [`data/`](data/README.md) is synthetic and generated by committed code: 200 fabricated claim notes with documented labelling rules and deliberate hard cases, and a fabricated term assurance valuation methodology. No real claim, policyholder, or insurer data was used anywhere.

## Governance

[`governance/`](governance/README.md) holds a machine-readable use case declaration, the prompt-log schema and a model card template. Local deployment solves the channel problem, not the governance problem: model governance obligations follow the model, wherever it runs. The declaration is the part example 04 reads at run time, so the governance position is enforced rather than asserted.

For the regulatory picture around all of this, [NIST AI RMF for Actuarial Boards](https://globebyte.com/insights/nist-ai-rmf-for-actuarial-boards) is a four-part series on why a voluntary framework became the de facto operational standard for insurance AI governance. It covers the strategic case, how ASOP 56 maps onto Govern, Map, Measure, and Manage, what the framework looks like across life, health, P&C, pensions, and reinsurance, and what the NIST Generative AI Profile adds. Part one opens with a thirty-minute board readiness assessment.

## Can LLMs do maths

Yes, and that is the wrong place to stop. Frontier models have real mathematical ability rather than a lookup table: one reached gold-medal standard on five of six International Mathematical Olympiad problems in July 2025. Competence is not the problem. Inspectability is. A model can show *a* working; it cannot show *its* working, and for anything that ends up in a reserving basis those are different claims.

So the rule this repository follows throughout: the model may choose the method, write the code, interpret the output, and draft the explanation, but the number itself comes from the code. That is why example 02 validates in code rather than trusting the reply, and why example 04 releases nothing until its citations resolve. [It Can Do the Maths. It Cannot Show Its Working](https://globebyte.com/insights/llm-mathematics-why-actuarial-computation-belongs-in-code) sets out the full argument, including why pushing arithmetic through a reasoning chain costs roughly ten trillion primitive operations to do what the hardware underneath does in a handful.
